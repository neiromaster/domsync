# Contributing

## Development

The Go toolchain version is pinned in `go.mod`. After cloning:

```sh
go build ./...
go test ./...
./scripts/check-coverage.sh
go tool golangci-lint run
go tool govulncheck ./...
```

Lint and formatting run through `golangci-lint` (including `golangci-lint fmt --diff`); do not reformat with other tools. `lefthook install` enables a pre-commit hook that runs gofmt, the linter, and the tests.

Fuzzing the parsers:

```sh
go test ./internal/domainlist -run '^$' -fuzz FuzzParseLocal -fuzztime 30s
go test ./internal/domainlist -run '^$' -fuzz FuzzParseRemote -fuzztime 30s
```

`internal/testutil/sshtest` runs an in-process SSH server, so sync end-to-end tests need neither a router nor network access.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/). Release notes are generated by git-cliff from commit subjects, and commits that do not parse as conventional are dropped from them, so a malformed subject silently disappears from the changelog.

```
feat(sync): adopt router-only domains on first run
fix(sshclient): negotiate the key type recorded in known_hosts
docs: add a pull request template
chore(deps): bump golang.org/x/crypto from 0.58.0 to 0.59.0
```

Common types: `feat`, `fix`, `docs`, `test`, `ci`, `build`, `perf`, `refactor`, `chore`. Scopes follow the package or area (`sync`, `config`, `domainlist`, `sshclient`, `update`, `report`, `release`, `deps`).

## Pull requests

- Branch from `main` and open a pull request; `main` is protected and accepts no direct pushes.
- Everything in the repository — code, comments, commit messages, PR titles and descriptions, docs, release notes — is written in English.
- Fill in the pull request template: what changed and why, how it was verified, and anything the reviewer must know.
- All required checks must pass before the merge: `test` on Linux, macOS and Windows, `lint`, `vuln`, `fuzz`, `coverage`, `dependency-review`, and CodeQL. The branch must be up to date with `main`.
- Pull requests are squash-merged; the branch is deleted automatically.
- Tests come with the change. Behaviour that depends on the router, the local file, or the update path is expected to have a test in `internal/testutil/sshtest` or with a fake runner rather than a manual check only.

## Code conventions

- Comments are rare: express intent through names and structure, and add a comment only where a non-obvious invariant or a workaround for an external bug needs one.
- Errors are wrapped with context and classified by the exit codes in the README; do not introduce a new exit code without updating the table.
- Configuration parsing stays strict: unknown fields, multiple YAML documents, and ambiguous input are errors, not warnings.
- Never write to the router or the local file before the whole plan has been validated.
- Actions in `.github/workflows` are pinned to full commit SHAs with the release tag in a comment; Dependabot updates the pins, so do not introduce floating tags.

## Releasing

Releases are maintainer-only. A release is a `v*` tag on a commit that is already on `main`; the workflow refuses any other tag. See the Release section of the README for the npm and Homebrew prerequisites.
